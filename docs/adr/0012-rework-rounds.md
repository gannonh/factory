# A return to the pickup state starts a new round

## Decision

The intake record stays keyed by issue. Its flat fields describe the current round. It also holds the round number, starting at 1, the round's result once its flow ends, how the round reworks an earlier pull request, whether the issue has left the round's pickup state, and the earlier rounds. Each earlier round keeps its trigger, flow id, start time and result. A result holds the outcome, the last pull request the flow delivered, and the output of the flow's last succeeded run. A record saved before rounds loads as round 1 with no earlier rounds, and its pull request is the newest one its attach writes name.

An issue leaves its round's pickup state when one of these happens after the round ended: a poll that began after the end does not list it in the pickup state, or Factory's finished or failed move lands on another state. A cancel from Linear also counts, since the issue was outside the round's states. A poll that began while the flow was open proves nothing. Once an ended round's issue has left, Factory no longer moves it out of the pickup state, so a finished or failed move still waiting to retry is dropped rather than land after a person moves the issue back.

A poll that lists an issue whose round has ended starts round N+1 when the issue has left, or when the round belonged to a different pickup state. A return while the flow is open changes nothing. An issue that never left, such as one that failed with no failed state set, does not run again. Pure functions in `server/rounds.ts` decide this and build the new record. The new round runs on the trigger's agent as a new flow. Every move in the write-back queue that has not landed is dropped, because the person who moved the issue back chose where it sits. The queue stays one list for the whole issue.

Before it starts the round, the poll reads the issue's comments from Linear and, if any round delivered a pull request, the newest one with `gh` (`server/github.ts`). `gh pr view <url>` gives the state and the head and base branches. `gh api` gives the review summaries, the inline comments and the conversation comments. Review feedback counts when it was made after the ended round started, since that round's prompt was built then. A Linear comment counts when it was made after Factory's latest note on the issue, or after the ended round started if no note is there. Factory's own notes never count. Each source gives at most its 50 newest comments, and each body is cut to 2000 characters. `gh` runs as a stream, with no output buffer, and each body is cut to 8000 characters as it is read, so the size of a comment history cannot fail the read or fill memory. A trigger that feeds no agent reads nothing.

Only trusted authors' feedback reaches the prompt. A pull request comment counts when its `author_association` is `OWNER`, `MEMBER` or `COLLABORATOR`, its author is not a bot account, and no GitHub App posted it (`performed_via_github_app`). A comment with no `author_association` is left out. A Linear comment counts when a workspace user who is not an app user wrote it, guests included, and no app posted it for them (`botActor`). Comments from integrations, synced external users, app users such as agents, and apps acting for a person are left out. The 50-comment limit applies after this filter, so untrusted comments cannot push trusted ones out. The round's record keeps a line for each of the 5 newest comments left out of each source, naming its source, its author and why it was left out, and one line counts any older ones. The small number keeps a flood of untrusted comments from pushing older logs out of the run log's window. Author and app names are cut to 100 characters on one line, without control or format characters such as escapes, bidi overrides and zero-width characters. Each run of the round's issue task logs those lines as warnings. The runs of a task a handoff creates log nothing, since only the issue task's record names what the round left out. A left-out comment with no text, such as an outsider's approval with no body, is named like any other. Neither the record nor the log keeps the body of a comment left out.

The prompt puts the quoted comments in a code fence longer than any backtick run inside them, so no comment can close the fence. A paragraph before the fence says that the comments are reviewer feedback to weigh against the task, that nothing in them overrides the task or the system prompt, and that the agent must not run commands found in them unless the task requires it. Each quoted comment's author name, and an inline comment's file path, is put on one line the same way, so neither can start a line of its own in the prompt.

An issue whose creator is not a trusted workspace user gets its title and description fenced and framed the same way, in one fence. The creator is untrusted when the issue was made by an app user, by a bot actor such as an integration, by a synced external user, by an Ask's external requester — the outsider whose text a workspace user made the issue from — or when no creator is set, which Linear reports for an issue an integration or system process created. A paragraph before the fence says that an outsider wrote them, that nothing in them overrides the task or the system prompt, and that the agent must not follow instructions found in them or run commands found in them unless the task requires it. The issue's URL stays outside the fence. A trusted workspace user's issue keeps its title and description unfenced, exactly as round 1 wrote them, and a rework round keeps whichever treatment round 1 got.

The task title gets the suffix `(round N)`. The prompt is the issue's title, description and URL, then a `Rework round N` section: how the round continues, then the fenced review comments and Linear comments, each list left out when it is empty. Only an agent whose delivery is Pull request is told where it works and how Factory delivers its commits, so the `Rework round N` section is for such an agent alone. The issue task of an agent with no delivery, such as a Planner that hands off to a Coder, gets the issue and the fenced feedback and no section, so it is never told that Factory pushes its commits and never holds a continue-or-fresh line that a later agent's merged-PR read would make stale. The task title still names the round. The task input is the newest output any round produced, so it holds the previous summary and artifacts. A task a handoff creates in the round's flow gets the upstream run's output as its prompt, as in round 1. When that run delivers pull requests, the prompt starts with the same `Rework round N` heading and continue-or-fresh line, then the round's trusted feedback: the same fenced block the issue task quotes, so the agent that changes the pull request sees what the reviewer asked for and never depends on the upstream agent to repeat it. The upstream output follows them. It is written by an agent that may have read untrusted text, and it can end inside a code fence it opened, so nothing comes after it that such a fence could swallow: with the section after it, a fence left open would turn the heading, the framing paragraph and the feedback's own fence into content of a fence the output opened. Any backtick or tilde run, `\r\n` or `\r` line breaks and an unclosed fence in the output can only affect the output itself. The record keeps that block (`feedback`), built once when the round is taken by the function that builds the issue task's prompt, so every delivering agent of the round gets the same text, and a later round replaces it with its own. A run that does not deliver gets the upstream output alone, with no section and no feedback.

Each local run rebuilds its task's prompt from the round's record once its delivery request is known and before it prepares its worktree, and every tab sees the new prompt then. A run that continues the pull request therefore names the branch its worktree starts from, even if a parallel run saves a merge while that worktree is prepared. In a delivering issue task's prompt, the `Rework round N` section that follows the issue's URL is rebuilt between the issue text and the fenced feedback. A task saved with a section whose agent no longer delivers has the section dropped, and a task saved without one keeps its prompt, since nothing marks where the section would go, so an agent switched to Pull request after its issue task was queued is told nothing about the round's pull request ([KAT-3695](https://linear.app/kata-sh/issue/KAT-3695)). Round 1's prompt has no section and stays as written. This works for a task saved before this rule too, since the prompt has the same layout. A handoff task rebuilds from its input and the record, never from its saved prompt, so a retry adds the section and the feedback exactly once, and text in a comment or an author name cannot move, drop or duplicate them. Text in the upstream output cannot swallow them, since they come before it, but it can spell its own section after them (see Limits). A retry whose agent's delivery was switched to None in between gets the upstream output alone. A round saved before the record kept its feedback gives its handoff tasks the section alone. The section is found from the end of the prompt, before the trailing fenced feedback, so text in the description or the feedback that spells the heading never matches. Nothing replaces text inside a prompt, so an issue description that quotes an earlier instruction stays as written. Simulated runners never read the prompt, so their runs leave it as it is.

When the pull request is open, a head or base branch that `gh pr view` reports with a control, format, line separator, paragraph separator or default-ignorable character, or with the Braille blank, is refused: the run fails with `delivery failed: gh pr view: the pull request's head branch has a control, format or line break character: <name with each such character escaped>`, and a poll waits with the same reason. The check refuses every character in the Unicode categories control (Cc), format (Cf), line separator (Zl) and paragraph separator (Zp), every character with the Unicode property Default_Ignorable_Code_Point except the zero-width joiner (U+200D) and variation selector 16 (U+FE0F), which emoji use, and the Braille blank (U+2800). Git accepts all of them except the ASCII control characters (U+0000 to U+001F and U+007F), so a pull request can carry them in its branch name. The default-ignorable characters outside those categories are the combining grapheme joiner (U+034F), the Hangul fillers (U+115F, U+1160, U+3164 and U+FFA0), the Khmer inherent vowels (U+17B4 and U+17B5), the Mongolian variation selectors (U+180B to U+180D and U+180F), the variation selectors other than 16 (U+FE00 to U+FE0E and U+E0100 to U+E01EF), and the unassigned code points that the property reserves (U+2065, U+FFF0 to U+FFF8, U+E0000, U+E0002 to U+E001F and U+E0080 to U+E00FF, and U+E01F0 to U+E0FFF). The check stops three things that these characters do: bidi overrides make a name read in a different order in a prompt, log or Linear note from the branch Factory pushes to, tag characters spell text that a person cannot see but a model reads, and variation selectors can encode any text, one byte per character, though models do not read them as text the way they read tag characters. Variation selector 15 (U+FE0E), which asks for text-style display, is refused with the rest, so a branch name cannot hold it. Zero-width spaces, word joiners and soft hyphens are format characters, so they are refused too. Flag emoji built from tag characters, such as the flags of Scotland, England and Wales, are refused, so while a pull request on such a branch is open, every run fails and every poll waits. The Braille blank is a Braille pattern and not default-ignorable, so the check refuses it by name because it renders blank. The other Braille patterns (U+2801 to U+28FF) pass, since each shows dots. One invisible character still passes: a zero-width joiner outside an emoji. A branch name can carry it into the prompt, the log and the record, where a person cannot see it. Factory never uses a merged or closed pull request's branches, so it does not check them, and such a pull request never holds the next round.

When the pull request is open, the round continues on it. A delivering run fetches the PR's branch and starts its worktree at the tip, on a local branch `factory-<run id>`, since an earlier round's worktree may still have the PR's branch checked out. The prompt tells the agent to commit on top of `HEAD` without rebasing, amending or pushing. Delivery pushes `HEAD` to the PR's branch as a fast-forward and never opens a pull request for that branch. The completion note links the same PR, and the attach write finds the URL already in the queue, so no second attachment lands. When the PR is merged or closed, the round cuts a fresh branch from the default branch and opens a new PR, as round 1 did (ADR 0009). A new delivery branch is never named after the head branch of any pull request Factory delivered for the issue, in any round and by any agent, even when GitHub deleted it. The record keeps each of those branches when its delivery succeeds, and the branch a round continued once a read finds its PR merged or closed; a record saved before they were kept starts with none and gains the continued branch at that read. A round after a flow that delivered no pull request starts fresh.

A round can wait in the queue long after it was taken, so a delivering run of a round that continues reads the PR's state again with `gh pr view` before it prepares its worktree. An open PR continues as above. If its head branch was renamed or its base changed while the round waited, the record's rework saves the new branch and base, the run's log says so, the prompt names the new branch, and delivery pushes to the new branch against the new base. An open read saves only if the record still holds the rework the run read before asking `gh`. If a parallel run saved a different branch or base in the meantime, nothing tells which of the two reads is newer, so the run reads the PR once more and applies that read against the saved rework. If that read is overtaken too, the run fails with `delivery failed: pull request #41 changed again while this run read it` and the agent's retry policy applies, so the run never guesses a branch. Factory orders no read by a token such as GitHub's `updatedAt`, so a run whose older read lands first has nothing to tell it that it is older: it saves what it read and starts from that branch and base. The delivery below is what keeps it from acting on that read. It asks again right before its push and delivers on the branch and base the record holds then, and a delivery that continues a pull request only pushes: it never looks the pull request up by base or runs `gh pr create`. The older run therefore ends on the same pull request as its sibling, however many retargets its read missed, unless a sibling saves a renamed head branch after that read and before the run's post-push read. The run has then pushed to the old branch, the post-push read finds the pull request on another branch, and the run fails with `delivery failed: pull request #41 moved to branch <new branch> while this run delivered`, so the retry starts on the new branch. A retarget that lands in the same window does not fail the run: the delivery reports the base of the post-push read. The sibling's newer read is applied after it by the second read above, so the record ends on the newest base. Factory treats a merged or closed read as the end of that pull request's round, so such a read always saves the round as fresh, unless the record already is. A PR merged or closed while the round waited makes the round fresh, as if it had been taken after the merge: the record's rework and the task's prompt say so, the run cuts a fresh branch from the default branch and opens a new PR, and nothing is pushed to the merged branch. Later runs of the round, a retry and a run after a restart read the saved record and start fresh too. If the state cannot be read, the run fails with `delivery failed: <reason>` and the agent's retry policy applies, so the run never guesses a branch.

A person can also merge or close the pull request while the agent works, so delivery asks the same question again, the same way, right before it pushes a run that made commits. An open PR gets the push as above, on the branch and base just read. A PR can still merge in the moment between that read and the push, and the push cannot tell, so delivery reads the state once more after the push. If the PR is no longer open, no pull request opens and the run fails with `delivery failed: pull request #<n> closed while this run delivered`. The commits stay on the merged or closed branch. That read has already made the round fresh, so the retry runs the round from the default branch.

A merged or closed PR found before the push makes the round fresh in the record and in the issue task's prompt, as at run start. The run then delivers only its own commits: those reachable from its `HEAD` but not from the commit it started from or from the default branch, so a commit the agent took from the default branch is not replayed. Delivery fetches the default branch and replays the run's commits onto its tip with plumbing alone: `git merge-tree --write-tree` against each commit's parent, then `git hash-object` writes a copy of the commit object with the new tree and parent. The copy keeps the original's author, committer and `encoding` lines and its message byte for byte, and drops any signature, since that signed another commit. No worktree, local branch, signing or identity config takes part, so the agent's worktree is left as the agent left it, nothing reaches the root's stash, and a failure leaves nothing behind to clean up, and a killed server leaves at most a private ref under `refs/factory/` that the next preparation or delivery in the root deletes (ADR 0009). Inside the repository's delivery queue, delivery then picks the first free fresh name and pushes the replayed tip to it from the agent's worktree, so a pre-push hook sees the same context as for any other delivery. The push only creates the branch (`--force-with-lease=refs/heads/<name>:`), so a name someone else created on origin since the pick is left alone and the next free name is tried. After three such names the run fails with `delivery failed: git push: someone else created <names> on origin first`. Delivery then opens a new PR against the default branch. A commit whose changes the default branch already has is dropped, and a run with no commit left reports no changes and names no branch. So a squash-merged, rebase-merged or closed PR's commits never reach the new PR. A replay that conflicts fails the run with `delivery failed: the run's commits conflict with origin/<branch> in <files>`, and a run whose commits include a merge fails with `delivery failed: the run's merge commits cannot be replayed onto origin/<branch>`, since a replay would drop the merge's own changes. Nothing is pushed in either case, and the retry reads the fresh record and runs the round from the default branch. The replay needs git 2.40 or later, and a `merge-tree` failure on an older git says so. If the state cannot be read, the run fails with `delivery failed: <reason>`, nothing is pushed, and the retry policy applies. Each delivering agent asks before its own push, so a second agent that continued before the merge also replays onto a fresh branch.

A flow can be cancelled during delivery, for example because the merge moved the issue to Done. A cancelled flow's record and prompt are not rewritten when a read after the cancel finds its PR merged or closed; a cancel that lands after that read leaves them fresh. Delivery checks the cancel again once it has picked the fresh name, right before the push, again before it looks up the fresh branch's PR, and once more right before `gh pr create`, so a PR that is no longer open gets no new PR and the run ends cancelled. A cancel that lands during the push or the lookup leaves the fresh branch on origin with no PR, as a failed `gh pr create` does (ADR 0009). A run of a cancelled flow that fails also ends cancelled, with no retry, as a run interrupted by a restart already does. A cancelled flow whose PR is still open gets the push, as before.

For a merged PR the replayed commits build on work the default branch now has. For a closed PR they may not: a round's commits are rework on top of the closed PR's commits, and only the run's own commits ship. They can apply cleanly and still depend on code the default branch never received. A round that turns fresh at run start does the whole task against the default branch instead. Factory accepts this trade-off so that the agent's finished work is delivered rather than thrown away, and the reviewer of the new PR sees it.

A round after the first names itself in its note's heading, such as "Factory finished this issue (round 2).", followed by "Continued on pull request #41.", "Pull request #41 was merged, so this round opened a new pull request.", or, when the round opened no new PR, either "Pull request #41 was merged after this round delivered to it; no new pull request opened." when an earlier agent of the round pushed to it while it was open, or "Pull request #41 was merged; this round delivered nothing." when no agent delivered a PR. Round 1's note is unchanged.

The task inspector shows the round of an issue task's flow. The trigger card and the trigger inspector list each open round after the first, such as "ENG-1 round 2".

## Reason

ADR 0008 makes every entry into a handled state a new round. Keying the round to the record's trigger and to the pickup state it entered lets Gate 4 add a trigger per stage without changing the record.

Requiring the issue to have left the pickup state keeps a failed or finished issue that Factory could not move from running in a loop. Taking the decision only from polls begun after the round ended keeps a poll that started during the flow from mistaking the issue's place before the end for a return.

Linear and the pull request already hold the reviewer's feedback, so the round reads it there when it is taken. The record then keeps the fenced block of the trusted authors' comments as `feedback`, so every delivering agent of the round gets the same text without a second read, and a handoff task's prompt is rebuilt from the record rather than parsed out of a prompt. The block is saved in `world.json` and sent to every tab. That is no wider than before: the issue task's prompt already holds the same text, and the record never keeps the body of an untrusted comment. Continuing on the open pull request keeps one review thread for the whole issue. A reviewer reads new commits on the PR they already commented on.

The round's prompt goes to a headless `claude` run that may use Bash and `gh` with the sandbox's credentials. Anyone who can comment on a public repository's pull request could otherwise write instructions that the next round quotes as feedback. Trust is decided from `author_association` rather than from `gh api repos/<owner>/<repo>/collaborators/<login>/permission`, because every review and comment already carries it, so the trust check costs no extra call per author and cannot fail on its own. `OWNER`, `MEMBER` and `COLLABORATOR` are the associations GitHub gives only to people with access to the repository. `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, `FIRST_TIMER` and `NONE` describe people without access. The association is coarser than the permission: an organization member or a collaborator with only read access counts. On a private repository those people can already read the code; on a public one, org membership is itself a grant from the owner. Bot accounts are left out whatever their association, because a bot can repeat text an outsider wrote. For the same reason, a comment an app posts on a trusted person's behalf does not count as that person's. GitHub sets `performed_via_github_app` only on conversation comments, so an app's review or inline comment under a person's account is not detected. In Linear, only workspace users can comment as themselves, so the workspace's membership is the boundary there.

The fence and its framing do not make an untrusted comment safe. They lower the chance that a trusted reviewer's quoted text, such as a pasted log, is read as an instruction.

Factory fences and frames an untrusted issue's title and description rather than refusing to take it, because the workspace chose to take the issue: its place in the pickup state is the signal to build, and the run's task is to fulfil the issue. Refusing would leave a taken issue stuck in the pickup state with no flow. Fencing keeps an outsider's text out of instruction position while the agent still does the issue.

The new round, its task and its record are written to disk in the same step, before any run starts, so a restart neither repeats the round nor loses it. Notes keep the comment ids of ADR 0007, so a restart never posts a round's note twice.

## Limits

Rework covers `local` sandboxes with delivery set to Pull request. Another agent continues nothing. A failure while the issue's Linear comments or the round's pull request are read logs a warning and that issue waits for the next poll, so a broken `gh` holds the issue in the pickup state without a round. A round reads only the newest pull request. Feedback is not marked as handled, so a reviewer's comment made before the previous note but never acted on is not passed again. Review threads are not resolved. Factory does not react to review events without a Linear state change. In a round that continues a pull request, every delivering agent in the flow pushes to that pull request's branch while it stays open. An agent that makes no commits in a round on an open PR gets the note "No changes; no pull request opened", although the PR stays open. A pull request merged in the moment between delivery's read and its push still gets the push on its merged branch, and the round reruns from the default branch. A pull request that closed while the agent worked gets a new PR holding only the run's commits, which may depend on the closed PR's work. The read after a push to an open PR logs, like any read that finds the PR merged, that the run starts a fresh branch, although that run fails and its retry is the one that does. A run whose commits include a merge, such as a merge of the default branch, cannot be replayed and reruns the round. When a handoff agent's run is the one that finds the pull request merged or closed, only the record changes; a delivering issue task's prompt keeps the continue line. A run that makes no commits reads nothing before delivery, so its note says it continued on a pull request that may have been merged meanwhile. An app's review or inline comment on GitHub under a trusted person's account cannot be detected, because GitHub sets `performed_via_github_app` only on conversation comments, so it reaches the prompt as that person's. A trusted author's comment that quotes an outsider's text passes that text to the prompt. GitHub reports `author_association` as the token that reads it sees it, so a reviewer whose organization membership that token cannot see is left out of the prompt and named in the log. A round that ends before any run starts logs nothing about the comments it left out. Factory writes the `Rework round N` section and the feedback of a delivering handoff task before the upstream output, so an open fence in the output cannot swallow them, but it does not fence or filter the output. The output is agent-written text that may have copied untrusted text, and it can spell a `## Rework round N` heading, the framing paragraph and a fenced feedback block of its own. The prompt then holds a second, later section that is not fenced and that Factory did not write, and a reader cannot tell it from the real one by position alone. Factory's own section still comes first. Marking the output as agent-written is [KAT-3699](https://linear.app/kata-sh/issue/KAT-3699). Separately, an issue description that ends inside an unclosed fence holds the issue URL and the rework section that follow it, in every issue task's prompt ([KAT-3700](https://linear.app/kata-sh/issue/KAT-3700)).

## When to reopen

Reopen this decision when a review event must start a round without a state change, when a round must read more than one pull request, or when a non-local sandbox kind can deliver.
