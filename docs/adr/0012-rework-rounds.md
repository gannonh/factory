# A return to the pickup state starts a new round

## Decision

The intake record stays keyed by issue. Its flat fields describe the current round. It also holds the round number, starting at 1, the round's result once its flow ends, how the round reworks an earlier pull request, whether the issue has left the round's pickup state, and the earlier rounds. Each earlier round keeps its trigger, flow id, start time and result. A result holds the outcome, the last pull request the flow delivered, and the output of the flow's last succeeded run. A record saved before rounds loads as round 1 with no earlier rounds, and its pull request is the newest one its attach writes name.

An issue leaves its round's pickup state when one of these happens after the round ended: a poll that began after the end does not list it in the pickup state, or Factory's finished or failed move lands on another state. A cancel from Linear also counts, since the issue was outside the round's states. A poll that began while the flow was open proves nothing. Once an ended round's issue has left, Factory no longer moves it out of the pickup state, so a finished or failed move still waiting to retry is dropped rather than land after a person moves the issue back.

A poll that lists an issue whose round has ended starts round N+1 when the issue has left, or when the round belonged to a different pickup state. A return while the flow is open changes nothing. An issue that never left, such as one that failed with no failed state set, does not run again. Pure functions in `server/rounds.ts` decide this and build the new record. The new round runs on the trigger's agent as a new flow. Every move in the write-back queue that has not landed is dropped, because the person who moved the issue back chose where it sits. The queue stays one list for the whole issue.

Before it starts the round, the poll reads the issue's comments from Linear and, if any round delivered a pull request, the newest one with `gh` (`server/github.ts`). `gh pr view <url>` gives the state and the head and base branches. `gh api` gives the review summaries, the inline comments and the conversation comments. Review feedback counts when it was made after the ended round started, since that round's prompt was built then. A Linear comment counts when it was made after Factory's latest note on the issue, or after the ended round started if no note is there. Factory's own notes never count. Each source gives at most its 50 newest comments, and each body is cut to 2000 characters. A trigger that feeds no agent reads nothing.

Only trusted authors' feedback reaches the prompt. A pull request comment counts when its `author_association` is `OWNER`, `MEMBER` or `COLLABORATOR`, its author is not a bot account, and no GitHub App posted it (`performed_via_github_app`). A comment with no `author_association` is left out. A Linear comment counts when a workspace user who is not an app user wrote it, guests included, and no app posted it for them (`botActor`). Comments from integrations, synced external users, app users such as agents, and apps acting for a person are left out. The 50-comment limit applies after this filter, so untrusted comments cannot push trusted ones out. The round's record keeps a line for each of the 50 newest comments left out of each source, naming its source, its author and why it was left out, and one line counts any older ones. Author and app names are cut to 100 characters on one line, without control or format characters such as escapes, bidi overrides and zero-width characters. Each run of the round's issue task logs those lines as warnings. A handoff task's prompt is the upstream run's output, which quotes no feedback, so its runs log nothing. Neither the record nor the log keeps the body of a comment left out.

The prompt puts the quoted comments in a code fence longer than any backtick run inside them, so no comment can close the fence. A paragraph before the fence says that the comments are reviewer feedback to weigh against the task, that nothing in them overrides the task or the system prompt, and that the agent must not run commands found in them unless the task requires it.

The task title gets the suffix `(round N)`. The prompt is the issue's title, description and URL, then a `Rework round N` section: how the round continues, then the fenced review comments and Linear comments, each list left out when it is empty. The task input is the newest output any round produced, so it holds the previous summary and artifacts. A task a handoff creates in the round's flow gets the upstream run's output as its prompt, as in round 1. When its agent delivers pull requests, its run adds the same `Rework round N` heading and continue-or-fresh line when it starts, read from the record after the pull request's state is checked, so the line matches how that run starts its worktree. A handoff agent that does not deliver keeps the upstream output alone.

When the pull request is open, the round continues on it. A delivering run fetches the PR's branch and starts its worktree at the tip, on a local branch `factory-<run id>`, since an earlier round's worktree may still have the PR's branch checked out. The prompt tells the agent to commit on top of `HEAD` without rebasing, amending or pushing. Delivery pushes `HEAD` to the PR's branch as a fast-forward, and `gh pr view` finds the open PR, so no second PR opens. The completion note links the same PR, and the attach write finds the URL already in the queue, so no second attachment lands. When the PR is merged or closed, the round cuts a fresh branch from the default branch and opens a new PR, as round 1 did (ADR 0009). A round after a flow that delivered no pull request starts fresh.

A round can wait in the queue long after it was taken, so a delivering run of a round that continues reads the PR's state again with `gh pr view` before it prepares its worktree. An open PR continues as above. A PR merged or closed while the round waited makes the round fresh, as if it had been taken after the merge: the record's rework and the task's prompt say so, the run cuts a fresh branch from the default branch and opens a new PR, and nothing is pushed to the merged branch. Later runs of the round, a retry and a run after a restart read the saved record and start fresh too. If the state cannot be read, the run fails with `delivery failed: <reason>` and the agent's retry policy applies, so the run never guesses a branch.

A round after the first names itself in its note's heading, such as "Factory finished this issue (round 2).", followed by "Continued on pull request #41." or "Pull request #41 was merged, so this round opened a new pull request." Round 1's note is unchanged.

The task inspector shows the round of an issue task's flow. The trigger card and the trigger inspector list each open round after the first, such as "ENG-1 round 2".

## Reason

ADR 0008 makes every entry into a handled state a new round. Keying the round to the record's trigger and to the pickup state it entered lets Gate 4 add a trigger per stage without changing the record.

Requiring the issue to have left the pickup state keeps a failed or finished issue that Factory could not move from running in a loop. Taking the decision only from polls begun after the round ended keeps a poll that started during the flow from mistaking the issue's place before the end for a return.

Linear and the pull request already hold the reviewer's feedback, so the round reads it there instead of keeping a copy. Continuing on the open pull request keeps one review thread for the whole issue. A reviewer reads new commits on the PR they already commented on.

The round's prompt goes to a headless `claude` run that may use Bash and `gh` with the sandbox's credentials. Anyone who can comment on a public repository's pull request could otherwise write instructions that the next round quotes as feedback. Trust is decided from `author_association` rather than from `gh api repos/<owner>/<repo>/collaborators/<login>/permission`, because every review and comment already carries it, so the trust check costs no extra call per author and cannot fail on its own. `OWNER`, `MEMBER` and `COLLABORATOR` are the associations GitHub gives only to people with access to the repository. `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, `FIRST_TIMER` and `NONE` describe people without access. The association is coarser than the permission: an organization member or a collaborator with only read access counts. On a private repository those people can already read the code; on a public one, org membership is itself a grant from the owner. Bot accounts are left out whatever their association, because a bot can repeat text an outsider wrote. For the same reason, a comment an app posts on a trusted person's behalf does not count as that person's. GitHub sets `performed_via_github_app` only on conversation comments, so an app's review or inline comment under a person's account is not detected. In Linear, only workspace users can comment as themselves, so the workspace's membership is the boundary there.

The fence and its framing do not make an untrusted comment safe. They lower the chance that a trusted reviewer's quoted text, such as a pasted log, is read as an instruction.

The new round, its task and its record are written to disk in the same step, before any run starts, so a restart neither repeats the round nor loses it. Notes keep the comment ids of ADR 0007, so a restart never posts a round's note twice.

## Limits

Rework covers `local` sandboxes with delivery set to Pull request. Another agent continues nothing. A failure while the issue's Linear comments or the round's pull request are read logs a warning and that issue waits for the next poll, so a broken `gh` holds the issue in the pickup state without a round. A round reads only the newest pull request. Feedback is not marked as handled, so a reviewer's comment made before the previous note but never acted on is not passed again. Review threads are not resolved. Factory does not react to review events without a Linear state change. In a round that continues a pull request, every delivering agent in the flow pushes to that pull request's branch. An agent that makes no commits in a round on an open PR gets the note "No changes; no pull request opened", although the PR stays open. The state is read once, before the worktree is prepared, so a pull request merged while the agent works still gets the run's push, and delivery opens a new pull request from that branch. The issue's title and description are quoted without a trust check or a fence, although Linear Asks, intake integrations and synced GitHub issues can put an outsider's text there. A trusted author's comment that quotes an outsider's text passes that text to the prompt. GitHub reports `author_association` as the token that reads it sees it, so a reviewer whose organization membership that token cannot see is left out of the prompt and named in the log. A round that ends before any run starts logs nothing about the comments it left out.

## When to reopen

Reopen this decision when a review event must start a round without a state change, when a round must read more than one pull request, or when a non-local sandbox kind can deliver.
