# Factory pushes the branch and opens the pull request

## Decision

An agent has a delivery setting: `none` or `pull-request`. The default is `none`. The agent inspector sets it, and a world saved before the setting existed loads every agent with `none`.

A run of a delivering agent on a `local` sandbox prepares its worktree differently. The server checks that the sandbox root is the top of a git repository with an `origin` remote. It reads origin's default branch, fetches that branch, and cuts the worktree from it, not from whatever the root has checked out. The branch is the issue's Linear branch name when the task belongs to an issue's flow, and `factory-<run id>` otherwise. When that name already exists locally or on origin, the run takes the first free name of `<name>-2`, `<name>-3` and so on.

When the agent's run succeeds, the server counts the commits on the worktree's `HEAD` since the run started, so commits the agent made on a branch of its own still count. With none, it opens nothing and adds the note artifact "No changes; no pull request opened". Otherwise it pushes `HEAD` to `<branch>` on origin. If `gh pr view <branch>` finds an open pull request the agent opened itself into the default branch, the server uses it. Otherwise it runs `gh pr create` against the default branch, naming origin's repository with `--repo` when origin is on GitHub. The title is the task title. The body is the run summary, followed by the issue URL for an issue task. The pull request becomes a `pr` artifact in the run's output before the run finishes, so a handoff carries it to the next agent. A failed push, a failed `gh pr create`, or a missing origin fails the run with the reason `delivery failed: <reason>`, and the agent's retry policy applies.

When an issue's flow ends finished or failed, write-back queues one attach write for each distinct pull request that the flow's succeeded local runs produced. `ensureAttachment` looks for an attachment with that URL on the issue and creates one only when none exists. Attach writes go out independently of moves, like notes. The completion note lists the run's artifacts, so it names the pull request or the "No changes" note.

Agents with delivery `none` work in a worktree on `factory-<run id>` from the root's HEAD, and Factory pushes nothing for them.

### When a run's worktree and branch are removed

A run's worktree at `<root>/.factory-runs/<run id>`, its registration under `.git/worktrees`, and the local branch Factory created with it are removed when the run ends, in any status: succeeded, failed, cancelled or interrupted. That branch is `factory-<run id>`, or the delivery branch for a new pull request. A branch already pushed stays on origin, and so does a pull request. Removal comes last in the run's end, after delivery pushed and opened the pull request and after the commit list was read for the run's output, because those are the only readers of the worktree. Everything else that outlives the run lives elsewhere: the output and its artifacts are saved with the run, the log is in the run log store, a handoff task carries the output, a retry or a rework round gets a worktree of its own (cut from origin for a delivering agent, from the root's HEAD otherwise), and no two runs share a local branch. A run that ends while its worktree is still being created is removed once the creation finishes.

Removal only takes what it can prove Factory made for that run. Before `git worktree add`, the server writes an owner file `.factory-runs/<run id>.owner` naming the branch, the commit the worktree is cut from, a random token, and the server process (pid and start time). The add runs with `--lock --reason <token>`, so git writes the token into the worktree's registration as part of creating it, before any `post-checkout` hook runs; an agent cannot lock the worktree again. Removal reads the owner file, then:

- The worktree goes, with `git worktree remove --force --force`, only when the registration at `.factory-runs/<run id>` carries the token. A worktree someone else made at that path stays.
- The branch goes, with `git branch -D`, only when its reflog begins with `branch: Created from <commit>` for the commit the owner file names; the add forces that reflog entry on. A branch someone recreated under the same name stays. A branch checked out in a worktree that stayed stays too.
- A branch the agent made in the worktree (`git switch -c`, `git checkout -b`, `git branch`) goes, with `git branch -D`, only when all of these hold. The branch was not among the local branches when the run began, which the owner file records, so an operator's branch the agent deleted and recreated stays. The first entry of its reflog says `branch: Created from <commit>`, and every entry was written after the second the owner file was created and no later than the run's end. The HEAD reflog of the run's worktree, which only that worktree has, has an entry that switched to the branch in the second the branch was created, at the commit it was created at. That is what `git switch -c` and `git checkout -b` write. A branch someone else made in the root, even during the run and from a commit of the run's branch, is switched to later and stays. Every entry of the branch's reflog also names a commit that HEAD reflog shows, so a commit made on the branch from another worktree keeps it. The creation commit is reachable from the run's branch, and no worktree other than the run's has the branch checked out. This is judged before the worktree is removed, because removal deletes that reflog; git keeps it while the worktree is registered, even when its directory is gone. The verdict is written to the owner file before anything is deleted, so a retry after a partial failure acts on it. When the worktree was already removed and no verdict was written, nothing ties a branch to the run, so each such branch stays and the warning names it. Every branch removed is logged with its name and tip, `removed branch <name> at <sha>; its commits can be recovered from that SHA until git prunes them`, in the world log and not in the run's output, which a later agent reads and which must not name a branch that is gone. Reflog times are whole seconds, so an operator who creates a branch and an agent who switches to it in the same second are not told apart. Factory cannot detect an agent that deletes a branch the operator made during the run and recreates it; it does detect one that does so to a branch that existed when the run began. `git branch -D` also deletes the `branch.<name>.remote` and `branch.<name>.merge` entries a `git push -u` wrote, and the pushed branch stays on origin. The run's end is the time the server saw it end, including a run that reset removed from the world. A run killed with its server has the time the next start recorded, and a run the server does not know has none, so its branches stay. A branch the agent created without switching to it (`git branch <name>`) stays. A branch with a reflog entry written after the owner file was created that fails any of these stays, and the run's warning names it and the failed condition. A branch made in the owner file's own second is treated as one that was already there. A branch with no reflog, such as one `git update-ref` made after the agent turned reflogs off, cannot be tied to the run and is neither removed nor reported. The run's output does not list a branch that is about to be removed.
- Any `refs/factory/<run id>/` refs go.
- The owner file goes last, after a success and after a refusal alike, so what was left alone is logged once, as a warning on the run, and not looked at again by that path. A worktree left under `.factory-runs` with no owner file is seen by every later start, as the next paragraph says. A failed git step keeps the owner file, is logged, and is retried at the next start.

`.factory-runs` must be a directory in the root, not a symlink: a run refuses to start through one, and removal refuses to delete through one. Removal deletes nothing itself except a token-carrying worktree whose `.git` file is gone, which git refuses to remove.

At start the server removes the worktrees of runs it does not know to be running: those the restored world marks interrupted, those the saved world never recorded because the save is throttled, and those a crash left half removed. A worktree whose owner file names another server process that is still alive, by pid and start time, is left alone with its owner file, whichever path reaches it: the start-up sweep skips it without a word, and a restore that marks its run interrupted, as when a second server starts on the same data directory, warns that the run's worktree and branch belong to the server still running. A pid alive with another start time was reused after that server died. A pid alive whose start time the owner file could not record counts as that server, since it cannot be shown to be reused. A worktree with no owner file, from before owner files existed, is removed only when this server's world knows its run to have ended, it is on `factory-<run id>` and it is not locked, since Factory never locked those and a lock there is someone else's. That removal is logged once, as an info line on the run that names the branch's tip commit, so an operator can recover unpushed commits by SHA until git prunes them. Any other worktree with no owner file is left alone and warned about at every start, since it may be another server's live run or someone's own worktree. A server from before owner files that is still working in such a worktree on the same data directory is not detected, since the worktree names no server. The next start does not look for an agent process that outlived a killed server, so such a process keeps running after its directory is gone.

A local sandbox's root cannot change while a run is on it, since the run's removal and the next start look under the root the sandbox has then.

Removal drops the commits an agent made in that worktree and that no push reached: a run with delivery `none`, a run whose delivery failed before its push, and a run killed mid-way. A succeeded run with delivery `none` still lists their branch and commit labels in its output, so a handoff task names a branch that no longer exists in the sandbox root, while its commits stay reachable by SHA until git prunes them. The branch goes anyway: a handoff may wait on a sandbox for any length of time, and a branch kept for it would be the leak this decision removes. A run that did not succeed has no output. A run in a root that is not a git repository works in a plain directory, which is not a worktree and stays. Locking the worktree needs a git whose `worktree add` takes `--lock --reason` (2.36 or later); on an older git every run in a git root fails with `git worktree add: <git's error> (locking the worktree needs git 2.36 or later; this is git <version>)`.

## Reason

Delivery must not depend on the agent remembering to push and open a pull request. A prompt can ask for it, but a run that forgets, runs out of turns or opens the PR against the wrong base still reports success. When Factory delivers, a succeeded run with commits always ends with a pull request, and a run whose delivery fails is a failed run that retries.

Credentials and naming stay with Factory. The agent needs no permission to push or to call `gh`, and the branch name and base branch come from one place instead of from each agent's prompt.

Linear's GitHub integration links a pull request to an issue when the PR's branch is the issue's branch name. Using `branchName` gets that link without Factory writing to GitHub beyond the PR itself. The attachment that write-back adds shows the PR on the issue even when the integration is not installed. Keying it by URL keeps a repeated write from adding a second one.

A retry never overwrites a pushed branch. An attempt that pushed and then failed to open its PR leaves that branch as it was on origin, and the next attempt pushes a suffixed branch. Nothing is force-pushed. An attempt whose push never happened leaves nothing on origin, and since its local branch is removed with its worktree, the next attempt can take the same name.

Removing a run's worktree keeps the sandbox root, which is often the operator's own clone, from collecting a worktree and a branch for every run. Left in place, those branches also made the first-free-name rule skip names for good, so later delivery branches drifted to `-3`, `-4` and higher.

Runs that share a root share its refs, and so do runs in a clone and its linked worktrees, which have different roots. The delivery queue is therefore keyed by the repository's shared Git directory (`git rev-parse --git-common-dir`, resolved to a real path), not by the sandbox root. A root that is not a repository queues by its own path. A push to origin also writes the pushed branch's remote-tracking ref, `refs/remotes/origin/<branch>`, and a fetch that writes the same ref while a sibling pushes it fails with `cannot lock ref`, which failed the run and burned a retry. That happened when a Reviewer started on a pull request's branch while the Coder pushed to it. So no fetch of Factory's writes a ref a push writes. Preparation and fresh-branch delivery fetch the branches they need with `git fetch --no-tags --no-write-fetch-head --refmap= origin +refs/heads/<branch>:refs/factory/<run id>/<n>`, read each commit from the fetch's own `--porcelain` output (git 2.41 or later), and delete the refs at once; `--refmap=` stops git from also updating `refs/remotes/origin/*` on the side, and `--no-write-fetch-head` leaves the shared `FETCH_HEAD` alone. Reading the tips from the output and not from the refs means a delete by another run, root or server cannot fail the run, so two Factory servers on one repository do not fail each other's runs ([KAT-3706](https://linear.app/kata-sh/issue/KAT-3706)). When a fetch ends, it deletes every `refs/factory/*` ref it can, and so does the start of the next fetch. Each ref is deleted on its own, so a ref with a stale `.lock` left by a killed git stays and the others still go; a delete that loses to another process leaves its ref for the next call. A run killed between its fetch and its delete, or a delete that failed, therefore leaves refs that the next fetch's delete, in a preparation or fresh-branch delivery in that repository, removes; no run id is reused, so nothing else would. The root's `refs/remotes/origin/*` are no longer refreshed by Factory, only by the pushes it makes. Only one push runs in the queue: a fresh branch's, together with the name it claims, so two runs never claim one name. A held fresh push blocks other runs' preparation in that repository until it ends. Every other push, a new branch's in the first round or a pull request's branch that a rework continues, stays outside the queue, so it neither waits for nor holds up another branch's push or another run's start. Serializing those pushes in the queue was tried and rejected, since it made deliveries to different branches take turns and let one slow push fail an unrelated run's timeout before its agent started.

Cutting from the fetched default branch keeps one run's local state from leaking into another's pull request. The sandbox root can have any branch checked out, with local commits, and the pull request still holds only the run's own commits.

## Limits

Delivery covers `local` sandboxes only. Simulated runs ignore the setting, and their demo pull request links are never attached to an issue.

The base is always origin's default branch. Merging, review and CI are out of scope, and a later attempt within one round opens a new pull request rather than pushing to an existing one. A rework round on an open pull request pushes to that pull request's branch instead. When that pull request is merged or closed while the agent works, delivery replays the run's commits onto the default branch and picks the fresh branch's name after the run, the same way and in the same queue. That push only creates the branch, so it never moves a branch someone else created (ADR 0012).

A retry after a failed `gh pr create` leaves the first attempt's branch on origin without a pull request. Nothing cleans it up.

Two delivering agents in one issue's flow each open their own pull request, on the issue's branch name and a suffixed one.

## When to reopen

Reopen this decision when a later attempt within one round must push to the existing pull request, when a base other than the default branch is needed, or when a non-local sandbox kind can deliver. ADR 0012 covers review rounds.
